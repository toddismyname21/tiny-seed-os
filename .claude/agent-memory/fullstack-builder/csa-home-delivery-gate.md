CSA portal "home delivery gate" (built 2026-05-24, commit 7413099 on csa-migration). Closed a revenue leak: members could self-select FREE home delivery. Owner policy: home delivery = $15/week, admin-approved, paid MANUALLY in Shopify. See also [[csa-portal-build-gotchas]], [[csa-pickup-nudge]], [[csa-management-api-implicit-txn]].

**The two-layer DB gate (migration 0030).** `change_pickup_location()` (the 3-arg RPC, originally migration 0016) was rewritten: SETTING a non-empty `delivery_address` now requires `is_admin_caller()` → member-initiated set returns `{error:'delivery_admin_only'}` and writes nothing; switching to a pickup STOP (which also clears delivery + any pending request) stays open to members. It's SECURITY DEFINER, so `is_admin_caller()` reads the CALLER's JWT (works through the member's RLS client = blocked, the admin's RLS client = allowed; service-role .rpc() carries NO JWT = also blocked — so admin delivery writes must go through the authenticated admin JWT, not service role).
- **Why a trigger too (the non-obvious part):** `members_self_update` (migration 0011) is `polcmd='w'` with `USING/WITH CHECK (customer_id = current_customer_id())` — it's ROW-scoped, NOT column-scoped. So a member could bypass the RPC entirely with a raw `supabase.from('members').update({delivery_address})` against the REST API using their own JWT. The RPC gate alone does NOT close that. So 0030 also adds a `BEFORE UPDATE OF delivery_address` trigger (`enforce_delivery_address_admin_only`, SECURITY DEFINER) that rejects setting delivery_address to a new non-empty value UNLESS `is_admin_caller()` OR `auth.jwt() IS NULL` (the JWT-less service-role/sync context). Members CAN still CLEAR delivery (move off it) and leave it unchanged while editing other columns — only a CHANGE to a non-empty value is gated. Proven: member direct-set blocked, member-clear allowed, admin-set allowed, service-set allowed.
- **Shopify sync is safe:** `src/pages/api/sync/shopify-orders.ts` upserts members via supabaseAdmin (service_role, no JWT → trigger exempts) and does NOT write delivery_address anyway.

**The request flow.** `/api/account/request-delivery` (member): marks the member's ACTIVE share(s) `home_delivery_requested_at = now()` + `home_delivery_requested_address` (member RLS self-update; these columns aren't gated, only delivery_address is), logs a `member_comms` row (channel `'other'`, via **supabaseAdmin** because member_comms is admin/staff-write only under RLS migration 0028), and emails `CSA_CONTACT_EMAILS` (Frankie+Todd, comma-split for Resend `to`) best-effort/fail-soft (`reply_to`=member). Idempotent — a "request pending" (requested_at set AND no delivery_address yet) shows "Request received…" instead of the form. `contact.ts` is a CLIENT mailto helper; the SERVER Resend send pattern to copy is `household.ts sendInviteEmail` (RESEND_API_KEY/RESEND_FROM_EMAIL from astro:env/server, fail-soft fetch to api.resend.com).

**Where staff see a request:** admin member-detail page (`admin/members/[id].astro`) — the Pickup card now shows a "Home delivery requested ($15/week — pending approval)" banner + the requested address (was "UI deferred until Phase 2"), the member_comms log entry, and the staff email. **Admin approval side:** that card's "Set pickup stop" + "Set home delivery ($15/week — approved)" forms POST `/api/admin/members/[id]/pickup` → change_pickup_location via the admin's `locals.supabase` RLS client (is_admin_caller()=true → delivery allowed). MUST use locals.supabase NOT supabaseAdmin (service role has no JWT → trigger/RPC would block).

**Member pickup chooser (`account/pickup.astro`) rewrite:** dropped the old free pickup/delivery radio `name="mode"` toggle entirely. Now: a pickup-STOP `<Select>` (posts /api/account/pickup-location, which is now pickup-ONLY) + a "Home delivery — $15/week, subject to approval" card with a textarea → /api/account/request-delivery. Members already on delivery (the ~15 already-paid, 66 with any delivery_address) render READ-ONLY ("Home delivery — <address>" + contactMailto "Contact us to change"). PickupNudgeBanner copy updated to "(or request home delivery — $15/week)".

**Seeding a home-delivery member in E2E (2026-06-05).** Because the trigger blocks ALL non-admin-JWT `delivery_address` writes (service-role included, no JWT), a test fixture CANNOT just `supabaseAdmin.from('members').update({delivery_address})` — it fails with `delivery_admin_only`. The working pattern (in `seedDashboardCardsFixture`, supabase-fixtures.ts): temporarily promote the test member's `customers.role`→'admin' (snapshot prior role), `mintMemberJwtClient(env)` (magic-link→verifyOtp, no email) so that member's JWT now passes `is_admin_caller()`, SET delivery via the `change_pickup_location` RPC (location=null+address=non-null is the valid one-of combo), then demote. CLEANUP restores via an admin-JWT DIRECT table update (not the RPC) because the RPC's one-of contract rejects restoring a NULL prior delivery_address. Forgetting to fully restore leaks delivery_address on the shared test member → breaks later-ordered specs (pickup-nudge expects `needsPickup`, runs serially `workers:1`).

**Verify pattern that worked:** RPC + trigger proven via Management API with `set_config('request.jwt.claims', ...)` to simulate member vs admin JWT, wrapped in `DO $$ ... $$; SELECT * FROM _tp; ROLLBACK;` (aggregate all scenarios into ONE temp table since the runner only prints the LAST statement's rows). E2E `home-delivery-gate.spec.ts` proves it end-to-end by minting a REAL member-JWT-scoped client (`proveMemberCannotSetDelivery` in supabase-fixtures.ts) and asserting BOTH the RPC `{error:'delivery_admin_only'}` AND a raw direct-update is blocked, delivery_address unchanged. Unaffected-members proof = same baseline COUNT query before/after (66/15/0 → unchanged; all test writes rolled back). DELIVERY NOT done by me — PM verifies + deploys.
