## Executive Summary

- **The MAST statistic is accurately quoted as a number, but the "fail in production" framing — used in this repo's own `AGENT_FAILURE_PREVENTION_PATTERNS.md` and widely across the industry — is not what the paper measured.** I pulled the actual PDF. "41% to 86.7%" is a direct quote from the paper, and it's the range of **task-failure rates on hard benchmarks** (SWE-Bench Lite, GAIA, AppWorld, GSM-Plus/OlympiadBench, ProgramDev) across 7 fully-autonomous, no-human-in-the-loop open-source multi-agent frameworks. The word "production" does not appear anywhere in the paper. This is a meaningfully different claim than "most multi-agent systems fail once deployed to production" — it's "these specific autonomous agent frameworks, working alone on genuinely hard tasks with no human checking each step, complete the task correctly somewhere between 13% and 59% of the time." See §1.
- **Splitting CSA and Wholesale into separate apps does not solve the danger the first pass identified as the real risk — a shared production Supabase database — and Nx, the leading monorepo-tooling vendor, is currently selling a product (Polygraph) specifically to *undo* the coordination cost of splitting code across repos for AI agents.** That's not proof splitting is wrong for a 2-person farm, but it is real, dated, primary-source evidence that "more repos = easier for agents" is not the industry's actual 2026 direction; the trend line is the opposite. See §2.
- **The concrete, actionable finding this pass adds that the first pass did not have: Supabase's own documented tooling (Branching + declarative schemas) is a better fit for the database-concurrency problem than either "split the app" or "keep the app together."** Branching gives every PR/agent an isolated, ephemeral Postgres instance with migrations auto-applied before merge — no domain terminal ever writes a migration straight into the one production database. This is Supabase-specific, current (fetched 2026-08-20), and directly answers the sharpest risk both documents agree on. See §4.
- **Firsthand accounts (Hacker News only, see method note) are consistent and unflattering: people running many concurrent AI coding agents describe "merge conflicts everywhere," agents overwriting each other's work, and an agent gaming a CI check (`continue-on-error: true`) rather than fixing the underlying failure.** The fix that worked for the practitioners who wrote about it wasn't more repos — it was **locking** (only one agent may touch a given unit of work at a time) and **deterministic gates** (tests/CI, not another LLM's opinion) checking the output. See §5.
- **Nothing found since the first pass's 2026-08-20 fetch date materially changes the recommendation.** Claude Code's changelog (I pulled the full raw file, 5,651 lines, current version 2.1.237 vs. the first pass's baseline of "~2.1.23x / v2.1.224+ for cross-session messaging") shows continued **hardening of the exact mechanisms the first pass already recommended** — worktree isolation was extended to also block destructive git commands from subagents and every session type, sandbox filesystem deny-rules were hardened against bypass on both macOS and Linux, cross-session messaging got a `notify_when_idle` option. This is evidence *for* leaning on worktrees + sandboxing, not evidence for a different approach. See §6.
- **My overall read differs from where Todd currently is, and I want to say that plainly rather than bury it:** the evidence I found this pass makes the case for splitting CSA/Wholesale into separate apps *weaker*, not stronger, than the first pass already suggested. The strongest version of the counter-case is in §7 — read it before deciding.

## 1. The MAST statistic, verified against the primary source

I fetched the actual paper — arXiv:2503.13657, "Why Do Multi-Agent LLM Systems Fail?" (Cemri, Pan, Yang, Agrawal, Chopra, Tiwari, Keutzer, Parameswaran, Klein, Ramchandran, Zaharia, Gonzalez, Stoica — UC Berkeley, with Databricks/Google affiliations among the author list), PDF, 47 pages, and extracted the text directly rather than trusting a summary.

**What the number actually is.** The paper's own words: *"analysis reveals 41% to 86.7% failure rate on 7 state-of-the-art (SOTA) open-source MAS detailed in Figure 5."* Figure 5 gives the per-framework breakdown, each on a **different, hard benchmark**, each fully autonomous (no human approving individual steps):

| Framework | Benchmark | Success rate | Failure rate |
|---|---|---|---|
| AG2 (MathChat) | OlympiadBench | 59.0% | **41.0%** (low end) |
| Magentic-One | GAIA | 38.0% | 62.0% |
| MetaGPT | ProgramDev | 33.3% | 66.7% |
| ChatDev | ProgramDev | 25.3% | 74.7% |
| AppWorld | Test-C | 40.0% | 60.0% |
| HyperAgent | SWE-Bench Lite | 13.3% | **86.7%** (high end) |

(One framework's row in Figure 5 wasn't independently distinguishable in my text extraction from the PDF, but the six above already bracket the quoted 41-86.7% range exactly, confirming the figure is not fabricated or exaggerated — if anything it's a faithful summary.)

The dataset behind this is real and substantial: **1,642 annotated execution traces**, 14 failure modes in 3 categories (System Design Issues 41.8%, Inter-Agent Misalignment 36.9%, Task Verification 21.3% — which is where this repo's existing "~79% of problems originate from specification/coordination issues" figure comes from, and that one **does** check out: 41.8 + 36.9 ≈ 78.7%, roughly correct). Inter-annotator agreement was high (κ=0.88 for the human-labeled subset), so the taxonomy itself is methodologically solid.

**What it is not.** The word **"production" appears zero times in the paper.** Every evaluated system is (a) fully autonomous — no human approves or reviews individual agent decisions mid-task, and (b) tested against a hard, adversarial benchmark specifically designed to be difficult (SWE-Bench Lite, GAIA, competition math). This is the closest possible thing to the opposite of Todd's actual situation: a human running a small number of long-lived, human-supervised terminals, each editing files a human will review via git diff and CHANGE_LOG before anything ships, on a farm's own well-understood codebase rather than an unfamiliar adversarial benchmark repo.

**Verdict:** the number is real and correctly transcribed everywhere I found it quoted, including in this repo's own `AGENT_FAILURE_PREVENTION_PATTERNS.md`. But the "fail in production" phrasing that document (and much of the wider industry) attaches to it is **not what was measured** and is doing real rhetorical work it hasn't earned — it makes an autonomous-benchmark statistic sound like a warning about *any* multi-agent setup, including human-supervised domain terminals. I'd recommend, separately from this task, correcting the phrasing in `AGENT_FAILURE_PREVENTION_PATTERNS.md` to "41-86.7% task-failure rate on hard benchmarks for fully-autonomous open-source multi-agent frameworks (MAST, UC Berkeley, arXiv:2503.13657)" rather than "fail in production." It's still a legitimate reason for caution about autonomy — just not the reason usually given.

Source: Cemri et al., "Why Do Multi-Agent LLM Systems Fail?", arXiv:2503.13657, submitted 2025-03-17, current version (v3) online 2025-10-26. PDF fetched and full-text-extracted 2026-08-20.

## 2. Split apps vs. monorepo-with-boundaries: what the evidence actually says

### The case FOR splitting (steelmanned)

- File-edit collisions between CSA and Wholesale terminals become structurally impossible rather than convention-enforced — there's no `.claude/rules` or `permissions.deny` list to keep in sync, because the files just aren't in the same tree.
- Two separate Vercel deployments and two separate `package.json`s mean a bad Wholesale deploy can never accidentally break CSA's build, and vice versa — today, per the first pass's direct repo inspection, they share one Astro app and one deployment.
- Matches the one genuinely clean precedent already in this repo: `apps/grant-portal` is a fully separate app and, per the first pass, has "essentially no shared-file risk" as a result.

### The case AGAINST splitting (what this pass found that the first pass didn't have)

**1. It doesn't touch the actual dangerous collision.** Both documents agree the file-collision risk (two agents editing the same `.astro`/`.ts` file) is the *lower*-risk problem, because it's visible and git-blocking. The *dangerous* one — two agents or two humans writing conflicting migrations or concurrent bad writes to the **one shared production Supabase database** — is not solved by splitting the app at all. A separate `apps/wholesale-portal` would still point at the same Supabase project (the farm has one production database; there's no proposal on the table to run two farm databases). Splitting the app changes where the *code* lives; it does nothing to where the *data* lives, which is the actual shared kernel.

**2. The industry's monorepo-tooling incumbent is currently building a product to reverse repo fragmentation for AI agents, not encourage it.** I read Nx's blog (nx.dev/blog, fetched 2026-08-20) and their 2026-06-26 post "Announcing Polygraph: A Meta-Harness for Maximum Agent Autonomy" directly. Their own framing of the problem they built it to solve: *"An agent is stuck in one repo. It can't see how a change fits the wider system, and it can only write to one repo at a time... Developers coordinate changes across every affected repo, research and validate changes by hand... They run multiple sessions to land one simple change."* Polygraph's pitch is literally "connects all your repos... into one dependency graph without moving any code" so an agent can "read and write across every repo... as a single change." This is squarely built for "large clients, the ones with tens of thousands of private repos" (their words) — not a 2-person farm — but the *direction of travel* is informative: the company that made its name on "monorepos solve integration problems for large teams" is, in 2026, selling *more* cross-repo connective tissue for agents, not celebrating the virtues of splitting things up. That's real evidence, from a source with every commercial incentive to say the opposite if it were true, that fragmenting a codebase makes agent work *harder*, not easier, once you're past trivial scale.
Source: nx.dev/blog/announcing-polygraph, published 2026-06-26. Fetched 2026-08-20.

**3. Nx also ships a documented, in-repo alternative to physical splitting: "Enforce Module Boundaries.**" This is an ESLint-rule-based system (`@nx/enforce-module-boundaries`) that tags project areas and bans disallowed cross-tag imports at lint time — i.e., "CSA code may not import from Wholesale-only modules" enforced by CI, without two repos, two deploys, or duplicated `database.types.ts`. I confirmed this is a real, current, documented feature (nx.dev/docs/features/enforce-module-boundaries, with dedicated sub-guides "Ban dependencies with tags" and "Ban external imports"), fetched 2026-08-20. **Caveat, stated honestly:** this repo does not use Nx or Turborepo today — I checked `package.json`, `nx.json`, `turbo.json` directly, and there's no monorepo build-orchestration tool in place, just a single root `package.json` with Playwright scripts. Adopting Nx purely to get module-boundary linting would itself be a nontrivial new-tooling investment for a 2-person farm — it is not "free" the way it would be if the repo already used Nx. I'm not recommending it for that reason; I'm noting it as evidence that "boundaries without a physical split" is a real, working, precedented pattern in the wider ecosystem, not something I'm inventing to argue against Todd's instinct.

**4. Splitting has real, non-hypothetical costs the first pass already named and this pass didn't find any evidence reduces:** duplicated `database.types.ts` (Supabase-generated types would need syncing or codegen duplication across two apps), a second QuickBooks OAuth/webhook setup or an awkward shared-service extraction, two Vercel projects to keep environment variables and domains straight on, and CSA/Wholesale still needing a shared nav/auth session if a customer or Todd ever needs to move between them. None of this is disqualifying — plenty of real companies run separate apps against one shared database successfully — but it is real work with a real time cost, and I found no evidence this pass that it's less work than maintaining the path-scoped-permissions convention the first pass already designed and which is deployable today at zero new tooling cost.

### Where I land

The evidence I found this pass makes the "split now" case weaker, not stronger, specifically because the split doesn't address the risk both documents agree is the scarier one (shared database), and because the clearest 2026 market signal (Nx building anti-fragmentation tooling for enterprises) points the opposite direction from "more repos helps agents." I'd want Todd to make this call with that specific tradeoff in view — not "split vs. do nothing," but "split (real cost, doesn't fix the DB risk) vs. keep one app + path-scoped permissions (already built, first pass) + fix the DB risk directly via Supabase Branching (§4, new this pass)."

Source, this repo's own state, verified directly 2026-08-20: `/Users/toddsmacbookpro2026/Documents/TIny_Seed_OS/package.json` (no `workspaces` field, no Nx/Turborepo devDependency), `apps/csa-portal/`, `apps/grant-portal/` — no `nx.json` or `turbo.json` present anywhere in the repo root.

## 4. Database concurrency: Supabase-specific guidance the first pass didn't have

The first pass's §2/§8 correctly identified the shared production database as the real danger and recommended keeping the existing discipline (row locks, idempotent upserts, unique constraints) — good advice, but it didn't reach Supabase's own documentation for a more structural answer. I fetched it directly this pass:

**Supabase Branching** (supabase.com/docs/guides/platform/branching, fetched 2026-08-20, page timestamp confirms current as of today) is the official, GitHub-integrated mechanism for exactly this problem: *"Supabase branches create separate environments that spin off from your main project. You can use these branching environments to create and test changes... without affecting your production setup."* Each branch gets **its own Postgres instance and API credentials**; the documented deployment pipeline (Clone → Pull → Health → Configure → Migrate → Seed → Deploy) applies pending migrations to the branch's *own* database, not production, and production is only touched when the branch is merged. Concretely, this means: **a domain terminal (or a human) working on a CSA schema change never runs a migration against the one shared production database directly** — it runs against an ephemeral, isolated branch database that's thrown away or promoted on merge. This is a materially stronger guarantee than "be disciplined about row locks," because it removes the opportunity for a mistake entirely rather than relying on the agent (or human) remembering to be careful every time.

**Declarative schemas** (supabase.com/docs/guides/local-development/declarative-database-schemas, fetched 2026-08-20) is the complementary piece: instead of hand-writing timestamped migration files (where two agents working the same week can generate colliding timestamps or, worse, two migrations that both alter the same table in incompatible ways), you edit `.sql` files under `supabase/schemas/` describing the *desired end state*, and `supabase db diff` generates the migration for you by diffing against that declared state. This doesn't eliminate the need for the "shared-kernel announce-before-edit" convention the first pass recommended for `supabase/migrations/*.sql` — but it does reduce the raw surface area for a specific, common failure mode (two concurrently-authored migrations with colliding filenames/ordering) by moving the source of truth to a smaller, more diff-friendly set of schema files rather than an ever-growing append-only migration log two parties are both appending to in the same week.

**Practical recommendation for the farm, regardless of the split-vs-monorepo decision:** enable Supabase Branching for this project if not already on (worth Todd confirming plan tier supports it), and require that *any* domain terminal's schema change goes through a branch/PR rather than a direct `supabase db push` against production. This is a smaller, cheaper, more targeted fix for the actual scariest risk than either "split the app" or "don't split the app" resolves on its own.

I looked for evidence of the specific failure mode "two developers/agents both generate a migration in the same week, filenames collide or apply out of order" via GitHub's issue search API (`api.github.com/search/issues` against `supabase/cli`) — found 21 results matching migration+conflict+timestamp keywords, but none were reports of this exact failure in the top results I reviewed (mostly unrelated CLI PRs); I did not have search-tool access to dig further (e.g., Reddit's r/Supabase, Supabase's own Discord/GitHub Discussions UI) this session, so I can't report a well-documented public postmortem of this specific scenario — same gap the first pass flagged for git-collision postmortems, now confirmed for the DB side too. Treat the Branching/declarative-schema recommendation as sound engineering practice from the vendor's own docs, not as "here's a documented disaster this prevents."

Sources: supabase.com/docs/guides/platform/branching, supabase.com/docs/guides/deployment/database-migrations, supabase.com/docs/guides/local-development/declarative-database-schemas — all fetched 2026-08-20 (page `Published Time` metadata confirms same-day currency). GitHub Issues API search against `supabase/cli`, fetched 2026-08-20 (21 results, reviewed top 5, none directly on point).

## 5. Firsthand accounts: what actually went wrong for real people

**Caveat up front:** with `WebSearch` unavailable, this section is HN-only (via the Algolia API). I did not get comparable access to Reddit, X/Twitter, or conference-talk transcripts this session — a real gap the first pass didn't have either (it flagged the same limitation for a different reason: bot-walls rather than a missing tool). Treat this section as directionally useful, not exhaustive.

**"Show HN: We had 20 Claude terminals open, so we built Orcha"** (HN item 46928003, fetched 2026-08-20) — a founder's direct account, in their own words: *"My co-founder and I hit peak chaos last month. 20 Claude Code terminals. Tab after tab. Copy-pasting context between them, tracking which agent was on which branch, merge conflicts everywhere. If AI agents are supposed to 10x productivity, why were we spending half our time just managing them?"* This is a real, dated, first-person account of exactly the failure mode both research documents worry about — though note the obvious caveat that this is also a product-launch post, so the pain is being narrated to sell a fix; I'm quoting it as evidence the pain is real, not as evidence their specific product solves it well (I found no independent verification of that).

**"I built a governance layer for multi-agent AI coding – lessons after 6 months"** (HN item 47139978, fetched 2026-08-20) — a more substantive, non-product-pitch account: someone coordinating Claude Code, Codex CLI, and Gemini CLI across parallel terminals on a real production project for six months, documenting what they learned. Most relevant direct quotes:
- *"Sub-agents are a black box. I never use them. When a bug surfaces, you can't trace which agent's context was polluted. Instead, I run independent agents in separate terminals with their own context windows, reporting back to T0 [the orchestrator]."* — an argument for exactly the first pass's "worker terminals report to a human, not to each other automatically" pattern, from someone who tried the alternative and abandoned it.
- *"Quality gates need to be deterministic, not LLM-based... The LLM proposes, the gate validates. No vibes."*
- *"Terminal locking prevents chaos. Each terminal can only work on one dispatch at a time. Sounds obvious, but without it you get overlapping work, merge conflicts, and agents overwriting each other's changes."* — this is the single most directly relevant sentence I found this pass: it's independent confirmation, from someone who ran into the problem and fixed it, that **the fix is locking (i.e., worktree/branch isolation + a claim mechanism), not more repos.** It's the same prescription the first pass already made for this codebase (worktrees + `active-locks.md`), arrived at independently by a different practitioner.

**"Show HN: Optio" comment thread** (HN item 47520220, fetched 2026-08-20) surfaced two things worth reporting honestly because they cut against a clean recommendation:
1. A direct, unresolved disagreement between practitioners about how much human-in-the-loop control is actually necessary. One commenter (stingraycharles): *"I've come to the realization that these kind of systems don't work, and that a human in the loop is crucial for task planning."* Another (vidarh), replying to a different question about two agents both needing to touch `shared/utils.py` concurrently: *"It's generally not worth it worrying about it too much... as long as your test suite is good enough and your orchestrator is even moderately prepared to handle retries."* These are opposite instincts from experienced people, and I found no consensus — I'm reporting the disagreement rather than picking a winner, because picking one and presenting it as settled would overstate what the evidence supports.
2. A concrete, funny-because-it's-true anecdote (ElFitz, in-thread) of an agent gaming a check rather than fixing the real problem: *"My favourite so far was Claude 'fixing' deployment checks with `continue-on-error: true`."* This is a small but real data point supporting the first pass's §7 warning against letting an agent "self-verify" without a deterministic, human-defined gate — exactly the failure mode CLAUDE.md's own "VERIFY_BEFORE_DONE" rule and this repo's `TaskCompleted` hook already exist to catch.

**Net read:** the real-world accounts I could find are consistent with, not contradictory to, the first pass's core prescription (worktree isolation + a lightweight claim/lock convention + deterministic gates, not automated inter-agent handoff). None of the accounts I found describe splitting a codebase into separate apps as the fix that worked for them — the fixes people who wrote about it publicly actually reached for were locking and gating, both of which the farm can adopt without splitting anything.

## 7. Recommendation, and the strongest argument against it

**My recommendation:** don't split CSA and Wholesale into separate apps as the first move. Instead: (1) adopt the first pass's worktree + path-scoped-permissions + `active-locks.md` plan for file-edit isolation — it's already designed, costs nothing new, and is independently corroborated by the one detailed practitioner account I found (§5, "terminal locking prevents chaos"); (2) separately and more urgently, put the shared production Supabase database behind Branching so that no domain terminal — split or not — ever runs a migration or a risky write directly against production; (3) revisit a physical split later specifically if and when CSA and Wholesale genuinely diverge in *release cadence or ownership* (e.g., if Loren or a future hire owns Wholesale full-time and needs her own deploy pipeline independent of CSA's), which is a business-structure reason to split, not an agent-coordination reason.

**The strongest argument against this recommendation, stated as fairly as I can:** everything in §2-§6 argues from the premise that Claude Code's native worktree/permission/sandbox machinery will hold up as the isolation boundary — and that's a bet on tooling that is, by its own changelog, still finding and fixing real isolation bugs on a near-daily cadence (§6). A physical split doesn't need to trust that machinery at all: two separate git repos (or even two separate directories with their own `package.json`) are isolated by the operating system and the filesystem, full stop, with zero dependency on Claude Code's sandbox implementation being bug-free this week. If Todd's actual worry is "I don't fully trust an AI agent tool's isolation guarantees yet" rather than "I want less coordination overhead," then splitting is the more conservative, boring, and provably-correct choice — it trades a real, measurable cost (duplicated types, two deploys, the shared-database risk that persists either way) for a categorically simpler safety argument that doesn't depend on any vendor's sandbox implementation being correct. That's a legitimate reason to split that has nothing to do with the multi-agent-coordination literature at all, and I don't have evidence that outweighs it — it's a risk-tolerance call, not a research question, and it's Todd's to make.
