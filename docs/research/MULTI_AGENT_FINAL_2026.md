## 1. Practitioner accounts, read in full

### The two `dev.to` posts named in the task

**dev.to/alanwest, "How to Coordinate Multiple Claude Code Agents Without Losing Your Mind"** (fetched and read in full, 2026-08-20; the post itself carries no date but references `claude-peers-mcp`, whose repo was created 2026-03-21, so it postdates that). This post's central example is exactly Todd's shared-kernel problem stated in different words: *"Agent A changes an interface, Agent B doesn't know. You get merge conflicts, broken contracts, and a lot of wasted tokens re-doing work... The core issue isn't that the agents are dumb. It's that they have no communication channel."* Its own honest caveat, worth repeating verbatim because it directly answers "when do we need this": *"for most day-to-day coding tasks, you don't need inter-agent communication... You probably don't need it when: Working on isolated features... The 'coordination' is really just you wanting to feel productive by running more agents."* Its recommended non-tooling mitigations — *"Assign clear boundaries: Give each agent a specific directory or module,"* *"Use the filesystem as a contract: Shared type definition files become the source of truth"* — are precisely pass 1's `permissions.deny` + shared-kernel-convention recommendation, arrived at independently.

A commenter (Max Quimby, in-thread) raises a question neither research pass had answered: in a peer-to-peer messaging model (as opposed to an orchestrator), *"How does the MCP server handle message ordering when two agents send conflicting intents simultaneously... Do you get an explicit conflict signal or does one agent just silently override?"* Nobody in the thread answers this. I checked `claude-peers-mcp`'s own issue tracker for the answer (see §2) and the honest answer is: **no** — see issue #81 below, where message delivery is documented as silently at-most-once while the database reports success.

**dev.to/sahil_kat, "Coordinate Multiple Claude Code Sessions on a Shared Repo"** (fetched and read in full, 2026-08-20). This one is native advertising for a product called Grass (published by the same author who runs `codeongrass.com`), and I'm flagging that plainly before quoting it — the failure-mode description is worth taking seriously, the product pitch that follows is not independently evaluated here. Its opening framing, sourced (per the post) from a Reddit r/mcp thread I could not independently verify (Reddit blocked every fetch attempt this session — see "Unverified" below), names three failure modes: *"conflicting writes that corrupt shared state... duplicate CI jobs triggered by parallel branch pushes... Browser MCP session state lost to 5-minute timeouts."* The most concrete and useful part, independent of the product pitch, is this description of what "last-writer-wins" actually looks like in practice: *"Two sessions editing the same file produce a last-writer-wins outcome... With agents operating at speed across dozens of files simultaneously, by the time you notice the conflict, one session's work may be entirely gone. No merge conflict marker, no warning — just overwritten."* That's a sharper, more concrete statement of the same risk pass 1 already named as the reason for hard `permissions.deny` boundaries rather than relying on convention alone.

Two more names surfaced only in that post's comment section, both real GitHub repos I verified directly (see §2 for detail): `garniergeorges/claude-presence` (advisory-lock MCP server, 12 stars) and `swoofer/mcp-coordinator` (MQTT-based coordinator, 1 star, last pushed the same day as this research). One comment from a second practitioner (maxime gagnon) is worth quoting because it directly contradicts part of the post's own advice: *"I tried explicit locks first and dropped them. They're advisory anyway, an agent can just ignore them, and in practice they don't always remember to check."* This is a real, first-person data point against relying on any advisory (non-tool-enforced) locking scheme — which is exactly why pass 1's recommendation leans on Claude Code's **hard** `permissions.deny` layer rather than a convention-only `active-locks.md` file for anything that actually matters.

### `crystl.dev`, "How to Run Two Claude Code Agents on the Same Repo Without Destroying Your Git History"

Fetched and read in full, 2026-08-20 (also product-adjacent — crystl is a worktree-automation tool — but the diagnostic section reads as straightforward and is corroborated elsewhere). Its clearest, most portable line: *"Git is designed for one writer at a time in a given working directory... Even if the agents are working on 'different files,' shared configuration files, lock files, and auto-generated code create unexpected collisions."* Directly relevant to this repo: `database.types.ts`, `quickbooks.ts`, and `package-lock.json`/`pnpm-lock.yaml` are exactly this kind of file.

### The two dated, quantified field logs

**devmoment.dev, "Git worktrees for parallel AI coding agents (2026)"** (fetched and read in full; dated 2026-07-02 in the article's own byline). This is the single most useful new source this pass found, because it is honest, quantified, and explicitly self-critical about the hype. Two weeks running three-to-five Claude Code agents in worktrees on a real side project, against a one-agent baseline:

| Metric | One agent (week 0) | Three-plus agents (weeks 1–2) |
|---|---|---|
| Tickets attempted | 9 | 34 |
| Merged clean | 7 (78%) | 21 (62%) |
| Reworked/thrown away | 2 | 13 |
| File-level conflicts | ~1/day | near zero |
| Rough token spend | ~$6/day | ~$19/day |

The author's own read, quoted directly because it's the clearest statement of the actual tradeoff I found anywhere this pass: *"Worktrees made me faster at generating work. They did nothing for the part that got slower: deciding what is safe to merge."* And the sharpest single sentence for Todd's specific plan: *"Worktrees fix the physical collision. They do not stop logic conflicts... Two agents, two folders, zero merge conflicts, and both quietly change how the same function behaves. Git sees no overlap. The tests pass in each worktree alone. They break when both land."* Their own practical ceiling, arrived at empirically rather than theoretically: **three concurrent agents** for a solo developer, because "review, not the agents, becomes the limit" beyond that — directly consistent with pass 1's "exactly four terminals, no fifth coordinator" recommendation, and a useful independent data point that four (CSA/Wholesale/Grants/Flowers) is already near the point where a human's review capacity, not the tooling, becomes the constraint.

**gptfrontier.com, "How to Fix Claude Code Multi Agent Git Worktree Collisions"** (fetched and read in full, 2026-08-20; a detailed technical tutorial, not obviously a product pitch, includes a working hook script). Its central, most important point for Todd's exact question — does worktree isolation touch the database? — is stated as plainly as I found anywhere this pass: *"Code Isolation is Not Environment Isolation... those folders still run on the exact same machine, sharing the exact same local resources... If your parallel sub-agents run local integration tests concurrently while pointing to a single development database file, they will corrupt each other's runtime data."* And its explicit statement of the exact scenario Todd is in — one shared cloud database, not local ephemeral ones — under "Conditions Under Which This Setup Will Break": *"Centralized Docker containers or shared cloud databases: If your integration tests connect to an external Docker container running on a fixed host mapping... your parallel agents will still pollute each other's data tables."* This is now the **fourth independent source type** (a practitioner tutorial, distinct from the academic paper, the vendor blog, and the GitHub issue) making the identical point pass 1 and pass 2 both already centered their recommendation on: **worktrees solve file collisions; they do nothing for one shared production database, split app or not.**

### `dev.to/battyterm`, "Git Worktrees Changed How I Run Parallel AI Agents"

Fetched and read (2026-08-20; also tool-adjacent, promoting "Batty"). Adds one useful, concrete anecdote and one practice worth naming: *"The first time I ran three AI coding agents on the same repo, they all edited `src/main.rs` within 30 seconds of each other. Two hours of merge conflict resolution later..."* — and the fix that stuck for them was running tests **per-worktree** so a failure is attributable to one agent's branch, not the combined state: *"With worktrees, each agent's tests reflect only that agent's changes against a clean baseline... If eng-2's tests fail, you know it's eng-2's code."* Worth folding into the farm's existing CI/testing practice regardless of the split decision.

## 2. `claude-peers-mcp` and comparable coordination tooling — assessed directly, not from the blog post

I did not stop at the dev.to write-up. I pulled the actual repository and its issue tracker.

**`louislva/claude-peers-mcp`** (`github.com/louislva/claude-peers-mcp`, fetched via GitHub API and raw README 2026-08-20): real, MIT-licensed, **2,196 stars, 300 forks** — genuinely substantial adoption for a niche dev-tooling repo, not a Show-HN toy. Mechanism: a `localhost:7899` broker daemon with a SQLite backend; each Claude Code session runs an MCP server that registers as a peer and can `list_peers`, `send_message`, `set_summary`, `check_messages`. It is explicitly peer-to-peer, not orchestrated, and explicitly **localhost-only** (no cross-machine support without extra work) — meaning it covers Todd's own CSA/Wholesale/Grants terminals talking to each other on one machine, the same scope pass 1 already identified native cross-session messaging as covering, but it does **not** natively bridge Todd's terminal to Loren's, same limitation as native messaging.

**Maturity, read from the repo itself rather than assumed:** created 2026-03-21, **last commit 2026-04-26** — roughly four months stale as of this research date. Only **2 contributors** (the author, plus one Claude-authored commit). **64 open issues** against a small codebase is a high ratio. I read all 7 of the most recent open issues directly:

- **#81 (2026-07-28), "Ghost peers are never reaped, and message delivery is at-most-once while the DB reports success"** — a detailed, reproducible bug report with a working patch attached: the broker's dead-peer reaper checks the wrong PID (the long-lived MCP server process, not the short-lived CLI session), so closed sessions accumulate as "ghost peers" indistinguishable from live ones. The reporter's own measurement: *"on my machine 5 ghosts accumulated over 4 days... a broadcast... fanned out to ~12 peer IDs; 5 were ghosts and several others no longer existed. Roughly half the messages went nowhere."* This is a real, current, unresolved reliability gap in exactly the mechanism the blog post recommends for Todd's use case.
- **#73 (2026-07-20), "claude-peers doesn't run on Windows"** — not relevant to Todd/Loren on macOS, but confirms narrow platform maturity.
- **#72 (2026-07-04), "Add repo-scoped work claims / leases for parallel sessions"** — an **open, unmerged feature request** proposing exactly the machine-readable "who owns which files right now, with a TTL" capability that Todd's farm already half-has, informally, in `.claude/rules/active-locks.md`. In other words: the most-starred tool in this space **does not yet have** the feature that would make it meaningfully better than the farm's existing convention — it's still a request, not a shipped capability.
- **#64 (2026-05-28), auto-summary silently failing** due to an OpenAI API parameter mismatch — a further reliability gap, and a reminder that the optional auto-summary feature sends session-directory/git-branch context to `OPENAI_API_KEY` by default, an external-data-sharing detail worth knowing before adopting.

**Its own quickstart recommends `claude --dangerously-skip-permissions`** to run the channel-mode integration — that flag disables Claude Code's permission-prompt system entirely, which is in direct tension with this repo's own `CLAUDE.md` security posture (path-scoped permissions as the *hard* enforcement layer pass 1 recommends leaning on). Adopting `claude-peers-mcp` as documented would mean giving up the one enforcement mechanism pass 1 identified as actually hard rather than advisory, in exchange for a *softer*, currently-buggy, four-month-stale messaging layer.

**Comparable tools found via the same search, verified via GitHub API (all fetched 2026-08-20):**

| Tool | Stars | Last push | Maturity read |
|---|---|---|---|
| `louislva/claude-peers-mcp` | 2,196 | 2026-04-26 (~4mo stale) | Most adopted by far; real but stale and buggy per its own issue tracker (above) |
| `garniergeorges/claude-presence` | 12 | 2026-07-24 (~1mo before research) | Tiny adoption, but actively developed (single maintainer, 20 merged PRs in ~4 months) — added "advisory resource locks," "counted locks (semaphores)," "warn when two sessions work on the same branch" through July 2026. The most feature-relevant to Todd's shared-kernel problem of anything found, but essentially unadopted (12 stars, solo maintainer, no track record) |
| `swoofer/mcp-coordinator` | 1 | 2026-08-20 (same day as this research) | MQTT-broker-based, cross-machine capable per its README (an explicit answer to `claude-presence`'s localhost-only limit) — but this is a brand-new, single-star, unreviewed project as of the day this document was written. Its author, in the dev.to comment thread, made a candid and useful point about *any* locking scheme: *"I tried explicit locks first and dropped them. They're advisory anyway, an agent can just ignore them"* (quoted in full in §1) |
| `adamripon-ship-it/claude-session-sync` | 0 | 2026-06-29 (one day of activity total) | Effectively a solo demo, not a track record |

**Assessment for Todd's farm:** none of these clear the bar of "adopt this instead of what pass 1 already designed." `claude-peers-mcp` has real adoption but is stale and has documented, unresolved message-loss bugs; `claude-presence` has the right feature set on paper but zero track record; the others are single-day projects. The pattern across all of them, read directly from source rather than inferred, is that **every one of them is still building toward "who owns which file, with a lease" — the exact capability the farm's `active-locks.md` already provides, informally, today, at zero tooling risk.** That's a genuinely new and useful finding this pass has that neither prior pass could reach: it's not that the farm is missing a tool the ecosystem has solved — the ecosystem hasn't solved it either, and the farm's manual convention is, right now, no less mature than the best-funded open-source attempt at automating it.

## 3. Split vs. monorepo-with-boundaries: two more independent lines of evidence

### Established service-architecture literature (new this pass, not AI-agent-specific at all)

Pass 2 leaned on one source for "splitting the app without splitting the data achieves little" — Nx's Polygraph announcement, a vendor blog with a commercial interest in the answer. This pass found the same conclusion in the field's actual canonical, decades-old reference, with no AI-agent angle and no vendor incentive either way:

**Chris Richardson (`microservices.io`), "Pattern: Shared database"** (fetched and read in full, 2026-08-20; Richardson is the author of *Microservices Patterns*, the standard reference text in this space — not a vendor selling agent tooling). Its stated drawbacks of exactly Todd's proposed architecture (two apps, one shared database) are named plainly: *"Development time coupling — a developer working on... the OrderService will need to coordinate schema changes with the developers of other services that access the same tables. This coupling and additional coordination will slow down development,"* and *"Runtime coupling — because all services access the same database they can potentially interfere with one another."* This is describing Todd's exact proposed shape (split app layer, shared data layer) as the textbook example of the *anti*-pattern, independent of anything to do with AI agents at all — the coordination cost pass 1/2 worried about for AI terminals is the same coordination cost this literature has documented for human teams for over a decade.

A second, independent, more blunt source (`archman.dev`, "Shared Database Across Services," fetched 2026-08-20) names the same architecture directly: *"You realize: this isn't microservices, it's a distributed application tightly coupled through the database."* Its "Design Review Checklist" question — *"Can you deploy one service without coordinating database changes?"* — is a direct, answerable test Todd can apply to a hypothetical split CSA/Wholesale: the honest answer today would be no, because both would still write to the same Supabase project.

**Net effect on the split-vs-monorepo debate:** pass 2's argument no longer rests on one vendor's product-launch blog post. It's now corroborated by the standard, vendor-neutral reference in service architecture, arrived at from a completely different direction (human-team coordination cost, not AI-agent tooling). Two independently-motivated bodies of evidence — one about AI agents specifically, one about human engineering teams generally — land on the identical conclusion: **splitting the app layer while keeping one shared database gets you the cost of a split with little of its benefit, for either kind of "developer."**

### A small-team-scale threshold (new this pass)

**`welldonesoftware.dev`, "Multiple Repositories vs. Monorepo: Lessons from the Field"** (fetched and read in full; dated 2026-03-03 in the post itself). Not AI-agent-focused at all — a general engineering retrospective — but directly on point for Todd's team size, which neither prior pass had a source for. Its concrete, experience-based threshold: *"for a small team of two to five part-time remote developers, a project split into more than seven to ten repositories already becomes painful to manage."* Todd's team (himself plus Loren, possibly a future hire) sits at the small end of that range, and the proposed CSA/Wholesale split would be one additional repo among four (grant-portal, and whatever Flowers becomes) — nowhere near that pain threshold on repo *count* alone, which is a mild point in favor of "a split wouldn't overwhelm the team mechanically." But its **decision matrix** cuts the other way for *this specific* split: *"Who changes the code? One team touches many components [→ leans monorepo] / independent teams own isolated components [→ leans multi-repo]... Do changes cross component boundaries? Frequently [→ monorepo] / Rarely [→ multi-repo]."* Today, per pass 1's own direct repo inspection, Todd (one person) touches both CSA and Wholesale code, and they share `database.types.ts`, `quickbooks.ts`, and `AdminShell.astro` — changes cross the boundary frequently, by this document's own test. That scores CSA/Wholesale on the monorepo side of this matrix specifically, even though the farm's total repo count is nowhere near this source's pain threshold.

## 4. Supabase Branching — what the 904-comment feedback thread adds

Pass 2 fetched Supabase's branching docs directly and reasonably concluded it was a strong, structural fix, while honestly flagging that GitHub Issues search on `supabase/cli` came up empty for a real-world postmortem. That search missed the right venue: not the `cli` repo's issue tracker, but Supabase's own **product feedback discussion**, `github.com/orgs/supabase/discussions/18937`, opened 2023-11-14, with **904 comments** as of this research date — found this pass in one search query, then read directly across pages 1, 8, 9, and 10 (i.e., both the early-adoption period and the most recent activity, current through 2026-08-16, four days before this research date).

**What's still true and good:** the mechanism is real, ships as documented, and the current price is modest — Supabase's own current usage docs (fetched 2026-08-20) state a Preview branch on the default Micro compute size costs **$0.01344/hour**, and a worked billing example in that same page shows a 30-hour-lived branch adding about **$1.40** to that period's invoice; run continuously that's roughly **$9.67/month per branch**, on top of the required $25/mo Pro plan. That's affordable for a farm's scale, and broadly consistent with what practitioners reported informally as far back as 2024 (a temporary+2-persistent-branch setup running "$55/month... it hurts a little").

**What pass 2 didn't have, and materially tempers the recommendation:** the thread's most recent substantive reports are not small UX gripes. Two, both from the seven weeks immediately preceding this research date:

- **2026-06-24 (chrisciszak):** *"When a new commit is pushed to a PR, supabase branch is not redeployed... In our case migrations were updated after the initial PR was opened... it allowed merging conflicting migrations into a persistent branch after which everything started failing."* — this is the exact failure mode ("two migrations collide on merge") both prior passes worried about, reported as **currently occurring**, in the tool that was supposed to prevent it.
- **2026-06-27 (nocodeanish):** *"I merged a dev → main pull request, and the linked Supabase dev branch was automatically deleted, taking down an active UAT database that a client was testing against. No warning, no confirmation, and the data is not recoverable... The problem is that it was too easy to end up without that protection, and the deletion was silent."* — unrecoverable data loss, from ordinary merge-time behavior, four months before this research date, on a feature that's been in general availability for well over a year.

And a direct, dated, considered practitioner verdict from partway through the thread (bzalk, 2026-04-02, after — by their own account — "watching this thread for a few months"): *"it's clear to me that right now supabase cloud branching is not worth the trouble/headache. So I've personally decided to move on and find a way to solve the problem for our team."*

**Revised recommendation, specifically because of this new evidence:** Supabase Branching is worth Todd trying on a **non-critical, single branch first** (a Wholesale-only schema change, say) before treating it as the farm's structural answer to database concurrency, and it should not be adopted with persistent, data-bearing branches until the 2026-06-27 silent-deletion behavior is understood and guarded against. **A cheaper, lower-risk interim fix, found this pass via a real practitioner issue** (`What-We-Will/community-platform` issue #78, "Resolve concurrent migration conflicts," closed, read directly, fetched 2026-08-20): the actual fix that worked for a real small open-source team hitting the identical concurrent-migration-numbering collision was **not** paid branching — it was (1) switching everyone to `supabase start` (free, local Docker Postgres, unlimited), (2) enforcing timestamp-based migration filenames (already the Supabase CLI default, eliminates numbering collisions almost entirely), and (3) a CI gate that blocks a merge if migrations are out of order relative to the current remote history. That thread also surfaced a second-order issue worth flagging for the farm regardless of which fix is chosen: *"It also is an issue if 1 dev makes a PR with migrations and one makes a PR without migrations after that one then the migrations don't go in since the DB has newer migrations than the latest PR"* (timchaffee, in-thread) — i.e., migration ordering can break even when only one side of a concurrent pair touches the schema.

## 5. Decision table

| Option | What it actually fixes | What it does not fix | Real cost | Evidence this pass |

## 6. Recommendation

**Don't split CSA and Wholesale into separate apps as the first move.** This pass adds two independent, non-AI-agent-specific bodies of evidence (established microservices literature, and a small-team monorepo-vs-polyrepo retrospective) to pass 2's already-reasoned case, and finds nothing — across five practitioner accounts, a maintained coordination tool's own bug tracker, and Supabase's own users — that argues splitting the app fixes the risk anyone actually cares about. **Adopt pass 1's plan** (worktrees, hard `permissions.deny` domain boundaries, and — the one part that needs to stop being aspirational — actually using `.claude/rules/active-locks.md` as a real claim/lease file before touching `database.types.ts`, `quickbooks.ts`, `AdminShell.astro`, or any migration). Cap concurrent terminals at four, consistent with the one quantified field log this pass found showing review capacity, not tooling, becomes the bottleneck beyond about three. Treat the database as a separate problem with its own fix — try Supabase Branching on one non-critical branch first rather than adopting it wholesale, given the 2026-06-27 silent-data-loss report is only two months old; if that trial goes badly, the local-Docker-Postgres-plus-timestamp-migrations approach a real small team used successfully is free and lower-risk. Do not adopt `claude-peers-mcp` or any comparable coordination MCP as a *replacement* for the `permissions.deny` hard-enforcement layer — at most, consider it later as a lightweight *notification* layer on top of that, once its message-reliability issues (documented, open, as of 2026-07-28) are resolved.

**The strongest case against this recommendation, stated fairly:** all three passes now agree the coordination story rests on Claude Code's own worktree/permission machinery, and on a human convention (`active-locks.md`) that this repo has had available and **not consistently used** since it was created. If the honest prediction is "the convention won't actually get followed under real time pressure" — which is a fair reading of `active-locks.md` currently being described in its own file as "no files currently locked" while multiple domains have clearly been under concurrent development — then a physical split has one advantage none of this pass's new evidence erodes: it's enforced by the filesystem and the OS, not by anyone remembering to update a markdown file before touching a shared type definition. That's not an argument that splitting fixes the database risk (it doesn't, per §2–§3 above) — it's an argument that if Todd doesn't trust the team (including future-Todd, at 6am on a delivery day) to actually maintain the shared-kernel convention, the file-collision half of the problem is worth solving with something that doesn't depend on discipline, even while the database half still needs a database-layer fix either way.
